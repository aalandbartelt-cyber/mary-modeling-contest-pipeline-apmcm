# 13 工件所有权与发布流程

> 本文件解决 2026 MathorCup 最严重的一次流程问题：辅助角色直接生成/覆盖正式论文和交付包，导致版本责任不清、用户明确要求返工。
> 适用：Codex / ZCode / dsh / 人类论文手 / 任何多智能体协作。

---

## 13.1 一句话原则

**正式工件只有一个写入者；候选稿不是正式稿；正式路径不接受“顺手改一下”。**

正式工件包括：

- 正式论文 DOCX/PDF；
- 正式图表（论文中引用的版本）；
- 正式交付包 ZIP；
- 正式审计合订本；
- `06_交付/` 下的提交物。

数据、图稿草稿、验证报告、评审意见不属于正式工件，可以并行写，但必须放在候选/证据路径。

---

## 13.2 角色与写权限

| 角色 | 可写 | 不可写 | 典型产物 |
|---|---|---|---|
| Codex（主） | `05_论文/正式/`、`06_交付/`、正式图目录 | — | 正式 DOCX/PDF、正式包、最终图 |
| ZCode（辅） | `05_论文/待审_YYYYMMDD/`、`04_图表/待审_YYYYMMDD/`、`docs/collab/` | 正式路径 | 数据表、图稿、验证、候选稿 |
| dsh（评审） | `docs/collab/reviews/` | 代码、结果、正式稿 | `REV-*.md`、评分、问题清单 |
| 论文手 | `05_论文/论文审阅与优化/` | 求解代码、结果 | 文字建议、审阅记录 |
| 任何人 | `_archive/` | 正式路径 | 旧版、快照 |

**硬规则**：

1. 辅助角色不得在正式路径执行 `Write/Edit/覆盖/重命名`。
2. 辅助角色如果必须改正式文件，只能提交 patch/差异清单，由主写入者应用。
3. 主写入者每次另存版本号，不覆盖上一版。
4. 评审角色只读；不得“顺手修一下”。

---

## 13.3 路径契约

```text
05_论文/
  正式/
    <赛事>_总论文_v<N>.docx
    <赛事>_总论文_v<N>.pdf
    <赛事>_论文审计合订本_v<N>.pdf
  待审_YYYYMMDD/
    <文件名>_待审.docx
    <文件名>_待审.pdf
    <文件名>_待审_验收.md
  证据/
    validation/
    figures/
    tables/
  归档/
    <旧版本>
06_交付/
  01_论文/           # 最终提交论文（A2601605.pdf 等）
  02_结果文件/       # 官方结果工作簿
  03_承诺书/
  04_支撑材料/
  A<队号>附件.zip
  提交清单.md
```

如果赛事要求 `05_交付/`，沿用赛事目录；原则不变：**正式与候选分开**。

---

## 13.4 候选转正式的五个条件

任何候选稿进入正式路径前，必须同时满足：

| # | 条件 | 证据 |
|---|---|---|
| 1 | 差异清单 | 文件、页、图、表、数字；新增/删除/修改 |
| 2 | 数值复核 | 正文 ↔ 结果 CSV ↔ 工作簿 |
| 3 | 版式检查 | 页数、目录、图表编号、表格不跨页、图题同页 |
| 4 | 语言/合规 | 禁用词、内部代号、身份信息、AI 声明 |
| 5 | 文件指纹 | 文件数、字节数、SHA256 |

建议在 `待审_YYYYMMDD/验收.md` 写：

```markdown
# 待审验收
- 来源/版本：
- 改动：
- 页数/正文页数：
- 图/表/公式：
- 数字核对：通过/不通过
- 禁用词：0
- SHA256：
- 建议：晋升/退回/仅作证据
- 主写入者确认：
```

---

## 13.5 发布清单（Release Manifest）

正式包必须带 `交付说明.md` 和 `SHA256SUMS.txt`：

```markdown
# 交付说明
- owner：Codex
- 版本：v<N>
- 论文：<文件名>，<页数>，正文 <页数>
- 附件：<文件名>，<文件数>，<字节>
- 结果：<文件名>
- 生成时间：
- 已通过：页数/目录/编号/OMML/禁用词/包内命令
- 已知边界：
```

`SHA256SUMS.txt` 覆盖包内所有文件；打包后回读校验。

---

## 13.6 冲突处理

- 两个角色同时要改同一文件：先停手，发消息确认唯一写入者。
- 发现正式文件被非 owner 改过：不要静默覆盖；先保存差异、回退、记录。
- 发现候选稿比正式稿“更好”：不要直接替换；走五个条件。
- 评审意见与主写入者冲突：评审只给建议，主写入者决定；决定写进 `decisions.md`。

---

## 13.7 本次案例

- ZCode 直接生成 Q1 v6、Q2 v5，并覆盖交付包；用户指出“这应该 Codex 做，你来做太不规范”。
- 后果：正式产物需要重新验收，Q2 包的原始字节被覆盖后无法按哈希恢复。
- 正确做法：ZCode 只交 `待审_20261027/` + validation + 图稿；Codex 逐项验收后生成正式版和包。

---

## 13.8 验收

- [ ] 正式路径的最近修改者 = owner；
- [ ] 每个正式版本有 `待审验收.md` / 发布清单；
- [ ] `git log` 中没有辅助角色直接改正式路径的 commit；
- [ ] 正式包有 SHA256 和文件数；
- [ ] 旧版未覆盖。
